Fehlersuche

Diese Seite ist nach Symptom sortiert. Suchen Sie Ihr Symptom – nicht die Ursache.

Die ComfoBox antwortet nicht

Symptom: Im Assistenten schlägt der Verbindungstest fehl (no_iam). Oder alle Werte bleiben leer.

1. Baudrate prüfen

Die ComfoBox muss auf 38400 Baud stehen und neu gestartet sein. Der Werksthypoten ist 76800.

Prüfen Wie
Baudrate am Bedienpanel der ComfoBox unter Service → Expertenebene
Neustart nach der Änderung zwingend neu starten

Die Baudrate wird nur beim Start gelesen. Ohne Neustart bleibt die ComfoBox bei 76800.

2. Verdrahtung prüfen

Kabel Anschluss
A A
B B

A und B vertauscht ist der zweithäufigste Fehler. Die ComfoBox antwortet dann gar nicht.

3. Adapter prüfen

Prüfung Befehl
Adapter sichtbar? ls -l /dev/serial/by-id/
Belegt? sudo fuser -v /dev/ttyUSB0
USB-Gerät da? `lsusb

4. Zweiter Master?

Wenn eine direkte BACnet-Anbindung aus Home Assistant aktiv ist, konkurriert sie mit dem Gateway um den Bus. Das Gateway verliert dann das Rennen.

Es darf nur einen geben. Gateway oder Direktintegration.

Das Paket lässt sich nicht installieren

Es gibt dafür drei verschiedene Ursachen – die Meldung im Paketzentrum ist immer dieselbe.

Symptom 1: „…da es mit Root-Rechten ausgeführt wird“

„ComfoBox Gateway kann nicht installiert werden, da es mit Root-Rechten ausgeführt wird. Pakete mit Root-Rechten können Befehle als Root-Benutzer ausführen und die Sicherheit Ihres Systems gefährden."

Ursache: Dem Paket fehlt die Datei conf/privilege. Ab DSM 7.0 verlangt Synology für jedes Paket eine ausdrückliche Rechteangabe – ohne diese Datei gilt das Paket als Root-Paket und das Paketzentrum verweigert die Installation.

Lösung: Sie brauchen eine neuere Version des Pakets. Ab 1.0.0-0002 ist die Datei enthalten.

Symptom 2: „…von einem unbekannten Herausgeber veröffentlicht“

Ursache: Sie haben das Paket manuell installiert (Datei auf die NAS kopiert). Das DSM kann den Herausgeber nur bei einer registrierten Paketquelle bestimmen.

Lösung: Über die Paketquelle installieren – Paketcenter → Einstellungen → Paketquellen → Hinzufügen:

Feld Wert
Name ComfoBox
Speicherort (URL) https://github.com/RF77/comfobox-mqtt/releases/download/v1.0.1/packages.json

Danach erscheint das Paket unter Community und wird von dort installiert. Sie müssen dafür keine Datei auf die NAS kopieren.

Symptom 3: „Paket kann nicht installiert werden. Versuchen Sie es später erneut…“

Ursache: Ein Skript des Pakets oder der DSM-Worker ist gescheitert. Die Meldung ist generisch – sie nennt den Grund nicht. Im Log des DSM steht dagegen genau, welcher Schritt geklappt hat:

grep -E "Acquire|failed" /var/log/synopkg.log | tail -10
Zeile Bedeutung
Acquire docker-project … (fail) Der Worker hat das Compose-Projekt nicht angelegt. Meist stimmt die Struktur von package.tgz nicht – oder es liegen Reste eines früheren Versuchs herum.
Acquire docker-project … (done) Der Worker war in Ordnung – der Fehler liegt in einem Skript.
End postinst ret=[0] Die Skripte liefen durch.

Den Grund nennt nur das Syslog, nicht synopkg.log. Der Worker schreibt nach /var/log/messages:

sudo grep -i -E "docker_project|comfobox" /var/log/messages | tail -20

Steht dort gar nichts, ist der Worker gescheitert, bevor er mit Docker gesprochen hat – dann liegt es am Zustand des Pakets (siehe nächster Abschnitt) oder an conf/resource.

Lösung: Holen Sie den echten Fehlercode mit dem Diagnose-Skript (unten).

Wichtig: „broken“ nach einem Fehlversuch

Schlägt eine Installation fehl, hinterlässt DSM 7.4 das Paket im Status „broken“ (150). Beim nächsten Versuch versucht DSM dann ein Update statt einer Neuinstallation – und scheitert an „package does not have preupgrade / postupgrade script“ (Fehler 261), obwohl das Paket in Ordnung ist. Zusätzlich bleiben Verzeichnisse, Container und Netzwerke des Fehlversuchs liegen – auch die lassen den Worker sofort scheitern.

Vor dem nächsten Installationsversuch deshalb aufräumen – ein Befehl erledigt alles (Paket deinstallieren, Verzeichnisse entfernen, Container und Netzwerke löschen):

sudo sh /tmp/dsm-diagnose.sh /tmp/<paket>.spk --reset

Das Docker-Volume comfobox-data bleibt dabei erhalten – dort liegt der 24-h-Schreibzähler (EEPROM-Schutz).

Meistens ist es die falsche Datei: Auf der NAS liegen oft mehrere .spk nebeneinander, und im Dateiauswahler wird die alte angeklickt. Prüfen Sie das so:

tar tf /volume1/pfad/zur/datei.spk | grep conf
# erwartet: conf/ und conf/privilege und conf/resource

Den echten Fehlercode holen

Das Paket wird mit allem Nötigen ausgeliefert. Das Diagnose-Skript liegt im Release direkt neben dem .spk (dsm-diagnose.sh):

# 1. SSH aktivieren: Control Panel → Terminal & SNMP → SSH-Dienst aktivieren
# 2. Verbinden
ssh admin@<IP-der-NAS>

# 3. Skript und Paket nach /tmp legen (von Ihrem Rechner)
scp dsm-diagnose.sh admin@<IP-der-NAS>:/tmp/
scp ComfoBoxGateway_noarch-dsm7_<version>.spk admin@<IP-der-NAS>:/tmp/

# 4. Diagnose ausführen - räumt zuerst auf und installiert dann
sudo sh /tmp/dsm-diagnose.sh /tmp/ComfoBoxGateway_noarch-dsm7_<version>.spk --install

Das Skript zeigt unter anderem:

  • die Struktur von package.tgz (muss auf der obersten Ebene liegen)
  • conf/resource und ob der dort genannte path zum Paketinhalt passt
  • die Compose-Datei und prüft sie mit docker compose config
  • die Reste früherer Versuche (Broken-Status, Container, Netzwerke) und räumt sie weg
  • den Fehlercode aus der JSON-Ausgabe von synopkg install
  • die Meldungen des Resource-Workers aus /var/log/messages
  • ob ein anderes Paket auf der NAS denselben Worker nutzt (Vergleich)

Die vollständige Anleitung steht in Synology testen.

Symptom 4: „failed to acquire postinst worker“ / „fail compose up“

Ursache: Der Container konnte nicht gestartet werden. Das DSM meldet nur „fail compose up“ – die eigentliche Docker-Fehlermeldung bleibt verborgen.

Das DSM-Log verrät, wie weit es kam:

grep -E "Acquire|failed" /var/log/synopkg.log | tail -10
Zeile Bedeutung
Acquire docker-project … (fail) Der Worker hat das Projekt nicht angelegt – die Compose-Datei wurde nicht gefunden.
Acquire docker-project … (done) Der Worker war in Ordnung – der Fehler liegt im Container-Start.

Lösung: Der Modus --worker macht exakt das, was der DSM-Worker macht, und zeigt die volle Docker-Fehlermeldung:

sudo sh /tmp/dsm-diagnose.sh /tmp/ComfoBoxGateway_noarch-dsm7_<version>.spk --worker

Das Skript entpackt das Paket wie das DSM, zieht das Image, prüft die belegten Ports und führt docker compose up aus – mit der vollständigen Ausgabe. Das Paket wird dabei nicht installiert; am Ende wird das Projekt wieder entfernt.

Ursache Kennzeichen in der Ausgabe Lösung
Image nicht ziehbar unauthorized / manifest unknown Image-Status prüfen (Schritt 0 in der Testanleitung)
Port belegt port is already allocated Anderen Port verwenden oder den Beleger stoppen
Verzeichnis fehlt no such file or directory Paket deinstallieren und neu installieren
Image passt nicht zur Architektur no matching manifest Image für linux/amd64 neu bauen

Keine seriellen Ports in der Liste

Ursache Lösung
Adapter nicht eingesteckt einstecken, Neu suchen klicken

Der Adapter wird manchmal erst später erkannt – besonders nach einem Neustart des NAS. Das Gateway wartet von allein und verbindet sich, sobald der Port da ist. Sie können aber auch selbst suchen: Neu suchen in der Port-Auswahl.

Die ComfoBox antwortet nicht

Symptom: Die Übersicht meldet „BACnet nicht verbunden".

Ursache Lösung
Falscher Port Port-Auswahl: richtigen Port wählen, Übernehmen (wirkt sofort)
Falsche Baudrate Baudrate 38400 einstellen (Werks-Default 76800)

Ein Portwechsel ist sofort wirksam – ein Neustart des Gateways ist nicht nötig.

Permission denied

Symptom: Das Gateway startet, aber keine Werte kommen. Im Protokoll: Access denied oder UnauthorizedAccessException.

Lösung: Der Benutzer im Container braucht die Gruppe dialout.

Betrieb Prüfung
Docker group_add: ["dialout"] in der Compose-Datei
Synology die USB-Regel des Pakets setzt die Rechte (siehe 99-comfobox-serial.rules)
HA-Add-on der Supervisor mappt den Port mit passenden Rechten
Raspberry Pi, Start ohne Container sudo usermod -aG dialout <benutzer>, danach neu anmelden

Auf DSM hat die Gruppe dialout üblicherweise die GID 20. Im Zweifel die numerische GID eintragen.

„Access denied" heißt nicht automatisch „keine Rechte". Unter Linux meldet .NET dieselbe Meldung, wenn der Port bereits geöffnet ist – das ist der Normalfall, wenn das Gateway läuft und ein zweiter Test ihn öffnen will. Der Assistent prüft das selbst: er nennt unter der Meldung die Fakten (Modus, Besitzer und Gruppe der Gerätedatei, Gruppen des Prozesses) und die daraus abgeleitete Ursache. Steht dort „die Rechte sind vorhanden", ist ein anderer Prozess der Halter – siehe Device or resource busy.

Device or resource busy

Symptom: Der Port ist belegt.

Ursache: Ein anderer Prozess hält den Anschluss offen – z. B. ein serial-getty, ein ModemManager oder ein zweites Gateway.

sudo fuser -v /dev/ttyUSB0

Achtung: Läuft bereits ein altes Gateway (z. B. der Mono-Dienst auf einem Raspberry Pi), muss eines davon abgeschaltet werden. Zwei Gateway auf einem Bus sind genauso problematisch wie zwei Direktintegrationen.

Home Assistant: Meldungen der MQTT-Integration

Die MQTT-Integration von Home Assistant schreibt beim Anlegen der Entitäten einige Warnungen. Keine davon bedeutet, dass die Heizung defekt ist. Die folgende Tabelle ordnet jede Meldung ein.

„Value … is outside of the range"

Symptom: Im Protokoll von Home Assistant steht zum Beispiel

Value 10 for number.comfobox_wiedereinschaltverzogerung is outside of the range 20.0 - 60.0

Ursache: Das Gateway liest einen Rohwert, der nicht zu den Grenzen passt, die es selbst als gültigen Bereich meldet. Drei Fälle sind bekannt – alle drei sind harmlos, aber unterschiedlich erklärbar:

Entität Wert Was dahinter steckt
Wiedereinschaltverzögerung (RestartDelay) 10 statt 20–60 Dieses Item und KühlraumsollAbstStandby lesen dasselbe BACnet-Objekt 864 (Altbestand). Der Rohwert 10 passt zum Standby-Absenkwert (0–10 K), nicht zur Wiedereinschaltverzögerung.
WW-Entladeschutz (Entladeschutz) 3 statt 0–1 Die Gerätedokumentation kennt nur 0 und 1; die Firmware der ComfoBox liefert auch 3. Die Katalog-Grenze ist zu eng.
HeatingHysteresis (Comfofond) 0 statt 2–20 0 heißt: Die Comfofond-Heizung ist nicht eingerichtet – dann ist die Hysterese unbenutzt und steht auf 0.

Was das für Sie bedeutet:

Aspekt Wirkung
Anzeige Der Wert wird korrekt angezeigt (10, 3, 0)
Regeln / Automatisierungen funktionieren
Schreiben dieser drei Werte wird abgelehnt (value_out_of_range), solange der Wert außerhalb liegt
Heizung kein Fehler – das sind Ist-Werte der Anlage

Was Sie tun können:

  1. Nichts – die Meldung ist dann nur ein Hinweis. Sie erscheint einmalig.
  2. Im Gateway-Protokoll (Diagnose → Protokoll) steht dieselbe Information als Warnung mit Item-Id, BACnet-Objekt-Id und Bereich. Das ist die verlässlichere Quelle als das HA-Protokoll.
  3. Wenn Sie einen dieser Werte schreiben müssen: erst prüfen, ob der Wert wirklich zu diesem Item gehört – bei RestartDelay ist das wegen der Doppelbelegung von Objekt 864 unsicher.

Warum meldet das Gateway es nicht als Fehler? Der Wert ist die Wahrheit des Geräts. Das Gateway übernimmt ihn unverändert; es korrigiert nie einen gelesenen Wert. Es protokolliert den Widerspruch einmal pro Item.

„Discovery topic … contains invalid characters"

Symptom: Meldungen zu Themen mit Umlauten, z. B. …kühl…, …überh…, …gebäudeträgheit.

Ursache: Die Topic-Namen der ComfoBox enthalten Umlaute. Sie sind Teil des MQTT-Vertrags und dürfen nicht geändert werden. Die Discovery-Kennungen von Home Assistant erlauben aber nur Buchstaben, Ziffern, - und _.

Lösung: Das Gateway schreibt Umlaute in Discovery-Kennungen seit dem letzten Update als ae, oe, ue, ss (aus Gebäudeträgheit wird gebaeudetraegheit). Die Werte-Topics bleiben unverändert.

Einmalige Nacharbeit nach dem Update: Für die betroffenen Werte legt Home Assistant neue Entitäten an. Die alten (mit Umlaut) bleiben als „nicht verfügbar" stehen und können unter Einstellungen → Geräte & Dienste → Entitäten gelöscht werden.

„… contains neither components nor child_devices"

Symptom: Warnung zu homeassistant/device/comfobox/config.

Ursache: Eine frühere Version hat zusätzlich eine eigene Geräte-Discovery veröffentlicht. Home Assistant erwartet dort eine Liste von Komponenten.

Lösung: Diese Nachricht wird nicht mehr erzeugt; das Topic wird beim Verbindungsaufbau mit einer leeren Nachricht entfernt. Die Gerätekarte entsteht aus den Entitäten und bleibt vollständig.

„Duplicate unique_id found"

Symptom: Zwei Entitäten streiten um dieselbe Kennung, z. B. sensor.wasser_messung_last_min.

Ursache: Meist stammt die doppelte Kennung nicht von diesem Gateway, sondern von

  • einer zweiten Gateway-Instanz mit derselben Kennung (Mqtt:DiscoveryIdentifier),
  • einer YAML-Definition in configuration.yaml, die denselben Wert anlegt,
  • einer anderen Integration mit gleichem Namen.

Prüfung: In Home Assistant die Entität öffnen → Einstellungen → Entitäts-Id und der Abschnitt Verwandte Meldungen nennen die Quelle. Bei MQTT zeigt das Zahnrad-Symbol das Discovery-Topic.

Lösung:

Ursache Lösung
zweite Gateway-Instanz Gateway:DeviceId und Mqtt:DiscoveryIdentifier unterscheiden; einmal neu starten
alte retained Discovery Topic mit leerer Nachricht löschen, z. B.
mosquitto_pub -r -n -t homeassistant/sensor/<kennung>/config
YAML-Entität den Eintrag in configuration.yaml entfernen

Schreiben läuft in die Zeitüberschreitung

Antwortet die ComfoBox auf Lesezugriffe (die Werte aktualisieren sich), aber auf keinen Schreibvorgang, liegt es fast nie an der Verkabelung.

  1. Protokoll ansehen (Diagnose → Protokoll). Steht dort WriteProperty (…) timed out und davor keine BACnet-Fehlermeldung, hat die ComfoBox den Auftrag nie bestätigt.
  2. Priorität setzen. Manche Stellwerte lassen sich nur mit einer Priorität schreiben. In der config.json (bzw. über die Umgebungsvariable COMFOBOX_Bacnet__WritePriority) 8 eintragen und den Gateway neu starten. Meldet die ComfoBox write-access-denied, ist das die Ursache – der Gateway schreibt diesen Hinweis dann selbst ins Protokoll.
  3. Bus beobachten. Unter Diagnose → BACnet-Bus lässt sich der Verkehr mitlesen: Kommt nach dem Schreibbefehl überhaupt ein Frame der ComfoBox zurück? Wenn nicht, ist der Auftrag auf dem Bus nicht angekommen.

Ein Schreibvorgang zählt nur bei Erfolg gegen das Tageslimit. Ein fehlgeschlagener Versuch verbraucht keinen Eintrag.

Werte sind veraltet

Symptom: In der Web-Oberfläche steht ein alter Wert; in Home Assistant ist die Entität unavailable.

Ursache Lösung
Adapter gezogen Adapter einstecken
ComfoBox ausgeschaltet einschalten
Port verstellt Assistent erneut durchlaufen

Der Gateway kennzeichnet veraltete Werte (älter als drei Abfragezyklen) und zeigt sie als „veraltet" an – nicht als aktuellen Wert. Das ist Absicht.

Die Energie-Werte fehlen oder stehen auf 0

Symptom: Wärmemenge, Stromzähler und COP fehlen in der Web-Oberfläche, oder sie stehen dauerhaft auf 0. In Home Assistant sind die Energie-Entitäten „nicht verfügbar".

Ursache: Der Regler rechnet die Wärme, er misst sie nicht. Er tut das nur, wenn am Gerät die Wärmemengenmessung eingeschaltet ist (Datenpunkt 3340). Bei Einstellung 0 rechnet er nicht: Die Wärmemengen bleiben an ihrem Startwert stehen, der COP bleibt leer.

Der Gateway erkennt das und veröffentlicht keine 0. Er markiert die Energie-Werte als nicht verfügbar und schreibt einmal pro Wechsel einen Hinweis in die Fehlerhistorie – sonst wäre die Energie-Statistik in Home Assistant dauerhaft verfälscht.

Lösung:

Schritt Was zu tun ist
1 am Regler auf der Service- bzw. Inbetriebnahme-Ebene die Wärmemengenmessung auf 1 oder 2 stellen
2 prüfen, ob der Durchfluss bei laufender Pumpe größer 0 ist
3 dem Zähler Zeit geben – er beginnt bei 0

Der häufigste Grund ist die ausgeschaltete Wärmemengenmessung. Die vollständige Anleitung steht unter Verbrauch und Effizienz.

Expertenmodus

Der Expertenmodus gibt zusätzliche Parameter frei, die das Regelverhalten der Heizung beeinflussen (Kurvenparameter, Grenzwerte).

Aspekt Wert
Aktivieren Konfiguration → Schreibschutz → Expertenmodus
Bestätigung ja, mit Rückfrage
Risiko falsche Werte können das Regelverhalten dauerhaft verändern

Nur mit Fachwissen aktivieren. Ein falsch gesetzter Parameter lässt sich unter Umständen nur durch einen Service-Einsatz zurücksetzen.

Gerätefehler und Gateway-Fehler

Symptom: Sie suchen einen Fehler der Heizung in der Fehlerhistorie und finden ihn nicht.

Das ist so vorgesehen. Die Fehlerhistorie (Diagnose → Fehlerhistorie) enthält ausschließlich Meldungen des Gateways: Verbindungsabbrüche, Zeitüberschreitungen, abgelehnte Schreibvorgänge, das erreichte Schreiblimit.

Die Fehler der ComfoBox stehen im Fehlerspeicher des Reglers am Display. Über BACnet sind diese Speicherplätze nicht adressierbar – der Gateway kann sie deshalb nicht lesen und zeigt sie auch nicht an.

Ort Inhalt
Diagnose → Fehlerhistorie Gateway: Verbindung, Zeitüberschreitung, Schreiblimit
Display des Reglers Gerätefehler mit Datum und Uhrzeit (zehn Speicherplätze)

Indirekt erkennbar ist eine Störung am Topic ComfoBox/States/HeatPump/HeatPumpStatus (Betriebszustand der Wärmepumpe). Diese Werte bedeuten eine Störung oder Warnung:

Wert Bedeutung
11…14 Störungen der Wärmepumpe
41, 46, 49 Störungen
53, 54 Störungen
61, 62 Störungen

Steht dort einer dieser Werte, sehen Sie am Display des Reglers nach, welcher Fehler ansteht.
